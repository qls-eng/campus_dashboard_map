# 复盘：从空壳仓库到可交付看板

## 一、起点是什么样

克隆下来时，这个仓库只有 6 个有用文件（`app.py`、`config.py`、`charts/analytics.py`、`charts/map_view.py`、`data/mock.py`、`data/weather.py`）和 6 个**0 字节的占位文件**（`charts/bar_chart.py`、`line_chart.py`、`pie_chart.py`、`table_view.py`、`data/campus.py`、`traffic.py`）。没有 README、没有 docs、没有数据文件、没有截图。

也就是说：**表面上"看板已经能跑"，实际上指导书要求的四件套（源码 / 截图 / 报告 / 博客）一件都没有**，而且数据层是空的。

## 二、最核心的问题不是"缺文件"，是"数据不同源"

原始 `charts/analytics.py` 每次页面 rerun 都调用 `mock.get_campus_data()`，里面用 `np.random` 现造人流数据。后果是：

- 顶部指标卡的"总人流量"和柱状图各柱之和**对不上**
- 表格里"三号食堂 1450"与饼图里的餐饮占比**对不上**
- 换一次筛选、刷新一次页面，所有数字都变

这直接违反指导书任务 5「结果验证」的"数据准确性"。所以这轮改造的第一件事不是画图，而是**先建唯一数据源**。

## 三、做法：先数据，后图表，最后整合

1. **第一版**写 `data/campus_flow_raw.csv`：17 个点位 × 2 天 = 34 条正常数据，另注入 7 条脏数据（空名称、名称带空格、负数人流、使用率 120、清单外摊位、重复行、日期格式混用）。
2. 写 `data/preprocess.py`：`load_raw → 规范名称 → 数值越界置空 → 同类型中位数填补 → 剔除清单外点位 → 按 (日期,建筑名称) 去重`，输出 34 行 clean CSV + 五条清洗报告。
3. 重写 `charts/analytics.py`：所有图表统一从 `load_clean()` 取数，`latest_flow()` 统一取最新一天，指标卡也走同一份数据。
4. 重写 `app.py`：四张指标卡 + 类型筛选联动 + 清洗摘要面板 + CSV 导出。
5. `charts/map_view.py` 增加"建筑人流量点位"图层，把 clean 数据与坐标合并上图。

结果（**第一版**）：清洗 41 → 34 行；指标卡 13,480 / 60.5 % / 三号食堂 1,450 / 17 个，与表格首行、柱图合计完全一致。

> 这套数据当晚被推翻重做：见第八节。第一版解决了"数据同源"，但没解决"数据可信"——使用率是独立随机数、所有数字都是 10 的倍数、峰值落到了食堂。

## 四、踩的坑与解决方式

| # | 问题 | 现象 | 根因 | 解决 |
| --- | --- | --- | --- | --- |
| 1 | 装依赖失败 | `WinError 32`：`websockets\cli.py` 被占用 | 往系统解释器的 site-packages 装包时文件被其他进程占用 | 改为项目内 `.venv` 安装，隔离环境；`.venv/` 已进 `.gitignore` |
| 2 | 截图全白 | Edge `--headless --screenshot` 只截到 Streamlit 顶栏 | 无头模式未等 WebSocket 连上，内容区尚未渲染 | 改用 Playwright 驱动本机 Edge，等页面末尾元素出现后再截 |
| 3 | 整页截图截不全 | `full_page=True` 得到的仍是视口高度 | Streamlit 内容放在内部滚动容器里，文档高度恒等于视口高度 | 直接把视口设成 1600×4200，一次渲染整页，再裁掉底部空白 |
| 4 | 以为折线图没渲染 | 页面只有 3 个 Plotly 容器 | 断言时页面还没渲染完（等待条件只等到"核心指标"） | 等待条件改为页面末尾的 caption 文本，等全后再断言：`stPlotlyChart`=4、`svg.main-svg`=12 |
| 5 | 弃用参数 | 日志刷了 6 条 `use_container_width` 弃用警告 | streamlit 1.66 已改 API | 6 处全部改成 `width="stretch"` |

坑 4 值得单独记：**截图和断言之前，先确认"页面渲染完成"的判据**。只看标题出现是不够的，长页面必须等最后一个模块出现。

## 五、做对的地方

1. **先定数据契约再写图表**：raw / clean 两份 CSV + 一个清洗函数，图表只读 clean，从根上避免"每个图各自造数"。
2. **故意注入脏数据**：如果原始数据本来就干净，清洗逻辑无法验证。第一版 7 条、第二轮 13 条，覆盖缺失、越界、重复、格式混用、清单外、文本空格六类，报告能逐条对应。
3. **指标卡与筛选解耦**：筛选只影响地图与图表，指标卡始终全量，并在卡片下注明统计口径，避免"筛选后总量变小被误读"。
4. **验证手段可复现**：把"截图/断言脚本"放在仓库外临时目录，仓库里只留成品图，避免把调试产物提交上去。

## 六、还没做好的

1. **没有自动化测试**：`clean_dataframe` 这类纯函数完全可以写 pytest，这轮只用了脚本断言 + 截图核对。
2. **图层开关 / 坐标拾取未逐项验证**：TC-15、TC-16 只确认了控件存在，没做点击比对。
3. **地图依赖在线瓦片**：断网时底图空白，只有点位按坐标画出来，体验打折。
4. **数据是模拟的**：README 与报告里都写清了；第二轮又把这一点推到界面上——天气取到 mock 时显示红色"演示数据"提示框，核心指标上方常驻数据来源说明（"清洗后的人流模拟数据集，按建筑容量与校园作息规律生成"）。

## 七、下次怎么更快

- 依赖安装先问"装到哪"：项目内 venv 比系统解释器更稳，也避免污染。
- 截图脚本模板化：Playwright + `channel="msedge"` + 超高视口 + 等末尾元素，这套组合可以直接复用。
- 先写"页面完成判据"，再写截图与断言；否则会反复怀疑代码有问题。
- 文档与代码同轮产出，不要留到最后补——补的时候细节（行数、指标值）已经记不清了。

## 八、第二轮整改（2026-11-18 晚）：从"数据同源"到"数据可验算"

### 触发点

部署上线后自查，两个问题把自己问住了：

1. "页面上 26℃ 是哪来的？"——桂林当天 13℃。
2. "人流最多肯定是教学楼吧？"——榜首却是三号食堂。

### 1. 天气是假数据，根因有三层

| 层 | 问题 | 解法 |
| --- | --- | --- |
| ① | Cloud 未配 Secrets，`config._get_secret()` 返回空串，`_get_mock_weather()` 静默接管 | Settings → Secrets 填入三个键 |
| ② | 手动粘贴时首行带了一句无 `#` 的裸文本，TOML 解析失败，三个键全部读不到 | 只保留 `KEY = "value"` 三行 |
| ③ | App settings 的 Python version 是 3.14，依赖装不上、部署持续失败，Cloud 保留旧容器 | 降到 3.12，重新部署 |

修完显示 13℃ / 61% / 28~37 km/h / 阴。同时加了两道防呆：mock 生效时页面红框明示；天气请求加 `@st.cache_data(ttl=300)`。

### 2. 数据重建模：从"随机数"到"可反算"

第一版的核心缺陷是**使用率与人流量互不相关**，`1230 / 79%` 这种组合算不出来。第二轮改成：

- 每栋楼先定"日累计接待容量"（教四楼 2800、图书馆 2500、行知楼按行政办公 900、食堂按座位×翻台……）
- `使用率 = 人流量 / 容量 × 100`，一位小数
- 类型活跃度区间 + ±5% 噪声 + 次日 ×1.08
- 种子取 `md5(建筑名|日期)`，重跑完全一致
- 注入 13 条脏数据（47 行），清洗后仍 34 行

结果：14,103 / 56.1% / 图书馆 2,271（90.8%）/ 17 个，环比 +10.7%；TOP5 为图书馆 > 教四楼 > 一号食堂 > 三号食堂 > 终点站，符合"教学楼多批次、图书馆全天自习、食堂只翻台两三顿"的常识。

> 第三轮又改了一次分类口径：最初把行知楼当"主教学楼"（容量 3500），它因此成为全站峰值。核对校方公开信息后确认行知楼是行政办公楼，改归"办公"类（容量 900、日累计约 370 人次），峰值回落到图书馆。这件事说明**模拟数据的"假"不只假在数字，也假在分类语义**——答辩时被问到"为什么行政楼人最多"就是硬伤。

另补 `campus_flow_hourly.csv`（48 行，三峰分布），并校验各小时合计等于当日总量。

### 3. 视觉：天气要压过核心指标

第一版把天气缩成一行小字，四个大数字最抢眼。改回 4 张卡置顶后又出现"四个框大小不一"——根因是 `st.metric` 高度随内容自适应（有的带 delta 行、有的 value 是长文字）。

解法：所有指标卡 `min-height: 136px` + flex 居中；天气组用 `st.container(key="weather_cards")` 命中 `.st-key-weather_cards`，加绿渐变、5px 绿边框、`2.35rem` 字号、`152px` 高度；核心指标收敛到 `1.5rem`。

### 4. 交互：定时刷新不再卡整页

`time.sleep(60) + st.rerun()` 会每 60 秒重建整页。改为 `@st.fragment(run_every=60)` 只重跑天气区块。

### 5. 部署：推了代码不等于生效

连推 4 个提交线上仍是旧版，`git ls-remote` 确认远程已更新，说明是 Streamlit 没拉代码。最终靠 **⋮ → Reboot app** 生效（Stop 只是暂停）。另外新版 App settings 的 General 里已不显示 Repository / Branch 字段。

### 6. 补上"点击图表联动"（进阶2 唯一缺项）

原先只有侧边栏筛选，指导书进阶2 要求的"点击某一图表分类，关联图表同步"没做。补法：

- 类型柱状图加 `st.plotly_chart(..., on_select="rerun", selection_mode="points")`，点击返回选区
- 选区里的 `x` 就是类型名，写进 `session_state.drill_type`，运行时用它二次过滤出 `drill_df`
- 地图、排行、饼图、明细表、仪表盘统一读 `drill_df`，顶部核心指标仍保持全量口径

这里踩了一个坑：第一版用"`picked != drill_type` 就同步"，结果每轮 rerun 都会把"取消联动"按钮设的 `None` 覆盖回旧类型，取消按钮形同虚设。改成记录 `drill_last_points`（上一轮观察到的选区），**只在选区相对上一轮发生变化时才同步**，点空白与按钮取消才都真正生效。

### 7. 这轮的方法论

- **数字要能当场验算**：抽查任何一行，`人流量 ÷ 容量` 必须等于表内使用率；抽任何一天，分时 24 小时求和必须等于日总量。
- **"看起来完整"≠"经得起追问"**：第一版解决了同源，但一问"这 79% 怎么来的"就露馅。
- **视觉优先级要写进 CSS，不能靠默认样式**：`st.metric` 不会自动区分主次。
- **交互状态要有"唯一真相 + 变化检测"**：联动这类靠 widget 事件驱动的功能，必须区分"用户刚点了"和"只是页面重跑"，否则取消类操作会被自动覆盖。
